# Amazon Listing Growth Pipeline

Use the conversation template in [references/conversation-template.md](references/conversation-template.md). Do not ask the user to create JSON or run commands. Treat uploaded CSV and XLSM files as attachments; write normalized JSON only inside the run directory for audit and recovery.

## Workflow

1. Parse the user message and attachments with `normalize_conversation()`. Ask only when a required item is absent or contradictory: marketplace, primary ASIN, at least one variant, brand/product type, price/cost, one keyword CSV, or one XLSM report. Normalize every variant as an independent `(marketplace, ASIN)` record with its own colour, dimensions and user-provided attributes; retain marketplace language, currency, variation theme and report-row evidence when available.
2. Run the ASIN page-evidence gate before building `listing_seed` or calling any derivative Skill. Invoke `scripts/fetch_amazon_evidence.py` with the requested marketplace, primary ASIN, competitors, and a run-directory evidence path. It uses a stable full browser request context, tries `/dp/<ASIN>` and `/gp/product/<ASIN>`, and records every URL, transport, status, final URL, parsed ASIN, title state, anti-automation signal, timestamp, and failure reason. A static record passes only when its final domain matches the marketplace, its parsed ASIN matches the requested ASIN, its HTTP status is successful, and its page Title is non-empty.
3. When the primary record or any competitor record is `needs_browser_evidence`, use `chrome:control-chrome` and the connected Chrome browser only. Do not inspect or export cookies, local storage, profile data, passwords, or session stores. For every record with that status, navigate normally to `https://<marketplace-domain>/dp/<ASIN>`, wait for the visible page to settle, then read the final URL and visible `#productTitle` text. If Chrome is unavailable, the page shows CAPTCHA, login, `automated access`, or another human-verification page, record outcome `unavailable` or `challenge`; do not ask the seller to complete a challenge and do not fall back to the in-app browser. Invoke `scripts/record_browser_evidence.py` for each observation to append it to the same evidence JSON, passing `--title-selector '#productTitle'` for an observed page. That script is the authority for browser evidence validation: it requires the marketplace domain, requested ASIN in the final URL, an `observed` page state, the exact title selector, no challenge signal, and a non-empty title.
4. Re-read the evidence JSON after all required Chrome observations. If the primary status is not `verified`, stop the workflow and deliver only the structured evidence failure diagnostic; do not build `listing_seed`, call Listing/Title/PPC/Rufus Skills, create frozen source outputs, create a sync plan, create an audit package, or create an XLSM copy. User product facts, keyword files, category reports, and model-generated text must never replace a missing primary page Title. If the primary gate passes, collect product facts and only verified competitor facts, then build a localized evidence-backed internal `listing_seed` without asking the user for Listing copy. For multi-variant runs, independently verify each child ASIN before generating or writing that child's Listing; an unavailable child blocks only that child action.
5. Competitor fetch or Chrome evidence failures are non-blocking evidence gaps. Record each failed ASIN and reason in the evidence file; never use an unverified competitor title, price, rating, review, bullet, or claim in Listing, PPC, review analysis, or search optimization. Only verified competitor fields may be used for comparison or keyword derivation.
5. Call `amazon-keyword-research`, `amazon-listing-optimization`, `kjxj-amazon-title-optimizer`, `amazon-product-compliance`, `amazon-review-analyzer`, `amazon-search-optimization`, and `amazon-ppc-campaign` in sequence. Capture and freeze each complete Markdown reply exactly as returned before calling the next derivation. Generate and freeze Listing Optimization and Title Optimizer output separately for every verified `(marketplace, ASIN)`; store them in `listings_by_asin`. `amazon-listing-optimization` and `kjxj-amazon-title-optimizer` are different sources: never substitute either reply for the other.
6. Call `run_conversation(..., raw_skill_outputs=...)` with the normalized task, generated seed, and captured replies. Required keys are `listing_optimization`, `title_optimizer`, `ppc_campaign`, `search_optimization`, `review_analyzer`, and `product_compliance`. Do not continue to review if any required reply is absent, its frozen attachment checksum changes, or the Listing reply does not contain a Title, five bullets, description, and backend search terms.
7. Before any XLSM write, generate frozen source attachments for every verified variant plus shared PPC and Rufus sources. Each variant has a separate complete, byte-for-byte Listing Optimization reply and Title Optimizer reply, indexed by `(marketplace, ASIN)` in a `variant-sources.json` manifest with its variant facts and verified evidence. Every sync action must repeat those variant facts plus preflight `product_id_type`, SKU, variation theme and report row; the report row must belong to that action. Do not merge, rewrite, omit or reuse one ASIN's Listing/Title source for another ASIN. The Rufus file concatenates the complete, byte-for-byte original search, review and compliance replies under their respective Skill headings. Add Chinese review translations only directly below English Q/A pairs, without changing the original Q/A or other source text. The Listing source must preserve the third-party Listing Title; a 2026 Title must never be written into it. Write a UTF-8 `path -> SHA-256` manifest for every frozen source. Invoke `scripts/build_review_package.py --variant-sources ...` with the variant manifest, shared PPC/Rufus paths, the frozen-source manifest, the read-only sync plan, the verified evidence JSON path, `<base>`, and the output directory. The script is the only approved builder for `*-sync-review.md`, `*-chinese-summary-review.md`, `overview.md`, and the SHA-256 manifest; never hand-compose those files with `apply_patch` or shell concatenation. The builder must reject every writable action missing a corresponding verified variant source or whose ASIN, attributes, row, or product ID preflight conflicts with the source. It must include every action's complete Listing, Title options, variant facts and XLSM target in the Chinese summary. Require its `status=ready`, preserve the checksum manifest, and verify every returned path exists, is regular, non-empty and UTF-8-readable before delivery. Deliver all variant attachments, the Chinese summary, and named `*-sync-review.md` as clickable, in-conversation Markdown preview links. State that no XLSM has been written. Ask only: `确认回填`.
6. After that exact approval, call `command_approve()`, which must invoke `kjxj-sync-product-listing` only. Validate the standard output name, source checksum, header rows, retained target/parent rows, deleted unrelated rows, written values, green fill, and OOXML integrity. Show [delivery.md] and provide the resulting XLSM with a Codex workbook output citation. Do not modify the source workbook.

## Evidence and Safety Rules

- Keep unverified facts as `Pending confirmation`; never turn them into claims.
- Keep child variant facts separate unless inheritance is verified.
- `listings_by_asin` is mandatory whenever more than one child ASIN is writable. Shared facts may be reused only when their source is identical and no child conflict exists. Colour, size, pack count, material, capacity, pattern, model and user-designated variation attributes are always ASIN-bound; missing values are `待确认`.
- Before XLSM apply, validate each action's marketplace, ASIN, product ID type, SKU, variation theme and variant attributes against its preflight row. A conflict blocks that action only. Never copy ASIN, row number or Listing text across marketplaces.
- Mark PPC defaults as assumptions: 15% referral fee, zero FBA/shipping fee, and daily budget 8. Never call the result a true break-even calculation.
- Treat missing review evidence as an evidence gap, not customer sentiment.
- A missing or invalid primary ASIN page Title is always a required-source failure and blocks the workflow. A verified primary page Title is not permission to infer unverified attributes.
- Treat `needs_browser_evidence` as an incomplete state, never as a passing primary gate. Browser-derived evidence must keep the failed static attempts and must be marked `source: chrome`; Chrome unavailable or challenge outcomes are failed evidence, never evidence of a product page.
- Detect anti-automation only from explicit page signals (`automated access`, CAPTCHA, `robot check`, Amazon validation path) or HTTP 429/503. Do not treat an arbitrary occurrence of the word `robot` as a challenge.
- Use Chrome as the only browser fallback. Never export browser-session data, bypass human verification, or use third-party product-data services as an evidence substitute.
- Continue through competitor and review evidence gaps only when they are explicitly recorded and excluded from downstream factual claims.

## Artifact Delivery Gate

- Treat a failed `apply_patch`, file-write command, checksum, or read-back as a failed artifact delivery. A failed patch is atomic unless independently proven otherwise; inspect the output directory before referring to any expected file.
- Use the editing tool's required unified-patch syntax exactly. In an `Add File` hunk, prefix every content line, including blank lines and lines inside fenced code blocks, with `+`. When an edit fails, do not assume a partial file exists.
- Verify with a read-only directory listing plus a non-empty UTF-8 read-back for the four frozen attachments, `*-sync-review.md`, `*-chinese-summary-review.md`, and `overview.md`. Validate every preview link against its exact existing absolute path.
- Keep an internal manifest of expected paths and SHA-256 values. A final user-facing preview link may be emitted only when its exact path is present in the manifest, passes the last read-back check, and is accompanied by a complete-content fallback plan.
- A clickable local Markdown link is a preferred preview mechanism, not proof of successful delivery. If the client does not expose a conversation preview for a link, immediately render the entire verified file content in the response. Do not provide only paths, filenames, link lists, or an overview as a substitute.

- The named `*-sync-review.md` audit package is the only approval gate. It must link to and then concatenate the complete contents read from the four frozen original-output attachment files without summarizing, parsing, rewording, omitting, or substituting content. The fixed order is Listing Optimization, Title Optimizer, PPC Campaign, then Rufus Q/A. Validate each embedded body against its frozen source checksum before delivery. Add only a uniform separator and source filename before each body. Immediately after the unchanged PPC body, add a `PPC 关键词复制区` derived only from that PPC Markdown: group positive keywords and negative keywords by campaign in separate code blocks, with one keyword per line and no bids, match types, explanations, or product-targeting ASINs. Block review generation when no PPC keywords or negative keywords can be parsed. Append the XLSM plan and `确认回填` instruction after the fourth body. The review must state that XLSM Title and Item Highlights use the separately selected 2026 title option; no 2026 value may be labelled as an original Listing field.
- Build `<base>-chinese-summary-review.md` as an additional audit attachment, not an approval gate and not a substitute for any frozen output. Its headings, field labels, explanatory text, risk notes, and audit translation must be Chinese. Preserve marketplace copy, keywords, campaign names, currencies, ASINs, and all other source-language values verbatim; do not use Chinese translation as Listing or XLSM data. The builder must extract and validate the normal Listing Title, 2026 short Title, Item Highlights, five bullets, description, backend search terms, every available PPC campaign, the `PPC 关键词复制区`, and Rufus Q/A from the actual frozen review files. Preserve every source Q/A and put its Chinese audit translation directly below it. If fewer than eight Q/A pairs exist, the upstream Rufus output must add only evidence-backed Q/A from verified specifications, variants, installation, care, or stated evidence limits and label unknown answers `待确认`; otherwise block package generation. Preserve all source Q/A when more than eight exist.
- Include `## XLSM 回填说明` in the Chinese summary before the evidence-boundary section. Generate it from the read-only preflight result and the normalized task without binding it to a marketplace, language, ASIN, product type, worksheet, or display-field name. State the output-copy naming rule, marketplace/report/worksheet/ASIN/parent evidence, selected 2026 title option, confirmed field mappings and sources, row handling, `#C6EFCE` change marking, preserved fields, and post-write OOXML verification. When preflight cannot establish a row, field mapping, or station evidence, state `待预检确认` or `无法执行`; never invent column names, row numbers, or write values. State that no XLSM has been written until explicit approval.
- Include the Chinese summary in `overview.md` and the SHA-256 manifest. Do not emit its preview link unless all seven audit files pass the final non-empty UTF-8 read-back and checksum verification.
- Do not render internal JSON keys, nested structures, or audit metadata such as `source`, `captured_at`, and `reports` in `*-sync-review.md`. Keep that data only in the JSON audit artifacts and manifest.
- Preserve every English question and answer in the review package. Add a Codex-generated Chinese review translation directly below each pair, label it `仅供审核`, and never write the translation back into Listing copy, original Skill replies, or source JSON. If a non-conversation integration does not supply a translation, show `待确认`.
- `delivery.md` links Listing, 2026 title, PPC, Rufus, compliance, search optimization, and the final XLSM. Internal sync JSON retains the third-party Listing fields in `listing` and the separately captured 2026 output in `title_options_2026`; the synchronizer uses the selected 2026 option only for Title and Item Highlights.
- The final workbook must use `YYYY-MM-DD_Amazon<站点>_分类商品报告_Listing同步完成_<ASIN数量>ASIN_vN.<扩展名>`. From row 7 onward, retain only updated child ASIN rows and direct parent rows; delete all other data rows and mark only changed Listing cells with `#C6EFCE`.
- Keep the CLI as an internal/developer compatibility interface only; never direct a seller to use it.
